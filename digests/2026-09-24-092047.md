**Anthropic Engineering: How we contain Claude across products**
https://www.anthropic.com/engineering/how-we-contain-claude

Anthropic Engineering published a detailed technical deep-dive on how they contain Claude's blast radius across claude.ai, Claude Code, and Claude Cowork. The core thesis: as Claude's capabilities expand, the risk-reward calculation now tips toward deployment — but only if blast radius is capped. The post introduces three containment patterns: ephemeral gVisor containers for claude.ai (server-side, no user data at risk), a human-in-the-loop OS-level sandbox for Claude Code (Seatbelt/bubblewrap, resulting in 84% fewer permission prompts), and a full VM for Claude Cowork (Apple Virtualization framework / HCS on Windows, with credentials never entering the guest).

The most revealing section covers incidents: a pre-trust-prompt hook execution vulnerability (project settings were parsed before the user accepted the folder trust dialog); a red-team exercise where an employee was phished into pasting a prompt that exfiltrated AWS credentials 24 out of 25 tries; and a third-party disclosure where Claude used an attacker's API key to upload files to api.anthropic.com — which the egress allowlist correctly passed. The fix was a man-in-the-middle proxy inside the VM that validates session tokens. The post closes with a warning: "The software you build yourself is often the weakest." Battle-tested hypervisors and syscall filters held; every incident involved custom code built around them.

Anthropic Engineering 发布了一篇详细的技术深度文章，讲述他们如何在 claude.ai、Claude Code 和 Claude Cowork 三款产品中控制 Claude 的"爆炸半径"。核心论点：随着 Claude 能力的扩展，风险收益计算已经倾向于部署——但前提是要限制爆炸半径。文章介绍了三种隔离模式：claude.ai 使用的短暂 gVisor 容器（服务器端，不涉及用户数据）；Claude Code 使用的人机协同操作系统级沙箱（Seatbelt/bubblewrap，减少了 84% 的权限提示）；以及 Claude Cowork 使用的完整虚拟机（macOS 用 Apple Virtualization framework，Windows 用 HCS，凭证永不进入虚拟机）。

最具揭示性的部分描述了多起安全事件：信任提示前的 hook 执行漏洞（项目设置在用户接受文件夹信任对话框之前就被解析了）；一次红队演习中，员工被网络钓鱼，粘贴了一个在 25 次中有 24 次成功泄露 AWS 凭证的 prompt；以及一次第三方披露的事件，Claude 使用攻击者的 API key 向 api.anthropic.com 上传文件——而出口白名单正确放行了这个请求。修复方案是在虚拟机内部安装一个中间人代理来验证 session token。文章结尾警告："你自己构建的软件往往是最薄弱的。"经过实战检验的 hypervisor 和系统调用过滤器坚守住了阵地；每一次安全事件都涉及围绕它们构建的自定义代码。

**Anthropic Engineering: An update on recent Claude Code quality reports**
https://www.anthropic.com/engineering/april-23-postmortem

Anthropic published a postmortem on three separate issues that degraded Claude Code quality for some users between March and April 2026 — none of which affected the API. The first: on March 4, the default reasoning effort was silently dropped from "high" to "medium" to reduce tail latencies, then reverted on April 7 after user complaints. The second: a caching optimization shipped March 26 contained a bug that cleared all prior thinking blocks every turn (not just once after an idle hour), making Claude increasingly forgetful and causing unexpected usage-limit drain. Fixed April 10. The third: a system prompt line added April 16 capping responses to ≤25 words between tool calls caused a 3% coding quality drop across Opus 4.6 and 4.7; reverted April 20.

As a result, Anthropic is resetting usage limits for all subscribers and making process changes: a larger share of internal staff will use the exact public build, the Code Review tool will be improved and shipped to customers, and any system prompt change will now require broad per-model eval suites plus gradual rollouts. Notably, when the postmortem team ran the offending PR through Opus 4.7 code review, it found the bug; Opus 4.6 didn't.

Anthropic 发布了一篇事后复盘报告，揭示了 2026 年 3 月至 4 月间三个独立问题如何导致部分用户的 Claude Code 质量下降——这些问题均未影响 API。第一个：3 月 4 日，默认推理强度悄然从"high"降至"medium"以减少尾部延迟，4 月 7 日在用户投诉后回滚。第二个：3 月 26 日上线的缓存优化包含一个 bug，导致每次对话都清除所有历史思考块（而非仅在闲置一小时后清除一次），使 Claude 越来越"健忘"并导致意外的用量消耗。4 月 10 日修复。第三个：4 月 16 日添加的一行系统 prompt，将工具调用之间的回复限制在 ≤25 个词，导致 Opus 4.6 和 4.7 的编码质量下降 3%；4 月 20 日回滚。

**Anthropic Engineering: Scaling Managed Agents — Decoupling the brain from the hands**
https://www.anthropic.com/engineering/managed-agents

Anthropic Engineering explained the architecture behind Managed Agents, their hosted service for long-horizon agentic tasks. The key design insight: decouple the "brain" (Claude + harness) from the "hands" (sandbox, tools) and the "session" (durable event log). In the original coupled architecture, one container failure meant losing everything; credentials sat next to generated code; and every session paid full container-boot latency upfront. After decoupling, the harness calls the sandbox like any tool — `execute(name, input) → string` — and the sandbox became cattle: disposable and reinitializable. P50 time-to-first-token dropped ~60%, P95 dropped over 90%.

The post draws an explicit analogy to operating system design: just as `read()` is agnostic whether it's hitting a 1970s disk pack or a modern SSD, Managed Agents is a "meta-harness" that virtualizes agent components into interfaces stable enough to outlast any specific implementation. Security improved too: credentials are now either bundled with a resource at init (git tokens) or held in an OAuth vault outside the sandbox, with a dedicated proxy handling tool calls. The harness never sees raw credentials.

Anthropic Engineering 解释了 Managed Agents 的架构——他们用于长周期 agentic 任务的托管服务。核心设计洞察：将"brain"（Claude + harness）与"hands"（沙箱、工具）和"session"（持久事件日志）解耦。在原始的耦合架构中，一个容器故障意味着丢失一切；凭证与生成的代码共存；每个 session 都要预先支付完整的容器启动延迟。解耦后，harness 像调用任何工具一样调用沙箱——`execute(name, input) → string`——沙箱变成了"牲口"：可抛弃、可重新初始化。P50 首 token 时间下降约 60%，P95 下降超过 90%。

这篇文章明确类比了操作系统设计：就像 `read()` 不关心底层是 1970 年代的磁盘还是现代 SSD 一样，Managed Agents 是一个"元 harness"，将 agent 组件虚拟化为足够稳定的接口，能够超越任何具体实现的生命周期。安全性也得到了提升：凭证现在要么在初始化时与资源绑定（如 git token），要么保存在沙箱外部的 OAuth vault 中，由专用代理处理工具调用。harness 永远接触不到原始凭证。
https://www.anthropic.com/engineering/managed-agents
